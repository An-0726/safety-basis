# 一、项目定位

Safety Basis 是一个面向安全生产 / EHS 实际工作的 **安全隐患整改依据知识库与速查网站**。

它不是单纯的法规全文库，也不是单纯的安全检查表数据库。

项目最终要解决的核心问题是：

> 当用户给出一条现场隐患、一张照片、一份检查记录、一份安全评价报告，或者一个新法规 / 新标准时，系统能够快速找到最合适、当前有效、可以解释为什么适用的法规或标准依据，并形成可直接用于专业工作的隐患描述、法规原文和整改措施。

用户最终不应关心后台数据库、Hash、事务、索引、迁移脚本等内部实现细节。

用户真正需要的是：

```text
现场隐患 / 图片 / 报告 / 新法规标准
                ↓
识别和规范化隐患
                ↓
查重、复用已有知识
                ↓
寻找最直接法规 / 标准依据
                ↓
核对法规身份、版本、条款原文和适用性
                ↓
必要时补充上位法 / 地方依据 / 兜底依据
                ↓
形成专业描述 + 原文依据 + 整改措施 + 适用说明
                ↓
进入结构化知识库
                ↓
经过校验和发布门禁
                ↓
更新速查网站
```

# 二、最终用户体验

网站和知识库应围绕现场工作，而不是围绕数据库结构设计。

用户输入可以包括：

- 隐患关键词；
- 一句话现场描述；
- 现场照片；
- 检查表；
- 安全评价报告；
- 法规名称；
- 标准编号；
- 新法规 / 新标准文件。

系统应能够输出：

1. **隐患专业描述**：把现场口语化问题转成适合检查、评价、整改通知等场景的专业描述；
2. **最直接法规 / 标准依据**：优先找真正针对该设备、行为、场所或技术要求的条款；
3. **法规 / 标准原文**：原文与解释分离，不允许 AI 润色后冒充原文；
4. **整改措施**：与隐患事实和引用条款对应，能够实际执行；
5. **适用说明**：说明为什么该条款适用于当前隐患，以及适用边界；
6. **必要的补充依据**：包括上位法、地方依据或其他 supporting basis；
7. **找不到直接专项依据时的兜底依据**：明确标记为 fallback，不把宽泛义务包装成直接技术条款。

网站应继续支持至少：

- 隐患关键词搜索；
- 场所类型筛选；
- 法规 / 标准类别筛选；
- 隐患详情查看；
- 法规 / 标准反向查询；
- 条款与隐患关系追溯；
- 当前依据与历史版本区分。

默认知识范围以国家层级为基础，并重点补充江苏省、南京市实际工作中常用的地方依据。

# 三、核心设计思想

Safety Basis V4 采用：

> **Git-first 维护 + Stable-ID 关系知识 + 实体级审阅绑定 + 内容型硬门禁 + 分级证据 + 自动 Release + 静态网站。**

V4 不推倒 V3 已经建立的知识资产，而是改变日常维护方式。

必须保留的核心思想：

- Stable ID；
- hazard、law、lawVersion、clause、link 分离；
- 同一条款可以被多个隐患复用；
- 同一法规的新旧版本必须分开建模；
- 法规替代关系必须保留；
- 国家、江苏、南京等 jurisdiction 独立建模；
- pending 与 verified 分离；
- 来源和证据可追溯；
- release 是构建产物，不是人工维护的第二母库；
- 候选 release 与生产网站分离；
- 不编造法规名称、标准号、条款号、原文、实施日期或效力状态；
- 不通过批量置信度或关键词相似度自动把内容升级成 verified。

# 四、整体系统架构

## 4.1 Google Drive：私有资料与原始证据层

Google Drive 主要保存不适合直接进入公开 Git 的资料，例如：

- 用户安全评价报告；
- 检查表和历史项目资料；
- Excel；
- PDF / Word；
- 合法持有的标准原件；
- 受版权限制的资料；
- 数据库快照；
- 全文库；
- 大型中间产物；
- 本地 AI 工作目录同步成果。

当前重要工作面为：

`ESH_Codex/work/safety-basis`

Google Drive 的作用是 **私有资料库和证据库**，不是公开网站的数据源。

---

## 4.2 GitHub：V4 日常正式维护面

V4 的结构化知识、项目设计、验证器、构建器和网站源码以 GitHub 为主要日常维护面。

核心知识目录：

```text
knowledge/
  manifest.json
  hazards/
  laws/
  law-versions/
  clauses/
  links/
  successions/
  reviews/
  evidence/
  provenance/
```

日常维护优先采用“一实体一 JSON”。

这样可以让 Chat 或其他 AI：

- 直接读取实体；
- 小范围修改；
- 精确查看 diff；
- 通过 Stable ID 找到关系；
- 使用 Git commit 追踪历史；
- 避免修改一个巨大 master 文件时产生大面积冲突。

---

## 4.3 SQLite：V3 冻结基线、迁移来源和分析工具

V3 `source/master/safety.sqlite3` 不删除。

在 V3 → V4 迁移完成前，它仍是 V3 的事实基线。

V4 稳定后，SQLite 主要承担：

- V3 历史冻结基线；
- 首次迁移来源；
- 数据回溯；
- 批量统计；
- 复杂查询；
- 必要时生成分析或交换产物。

SQLite 不再要求成为用户以后新增一条隐患时必须直接操作的入口。

---

## 4.4 Excel：查看、交换和批量审阅工具

Excel 保留，但不作为第二事实源。

主要用于：

- 人工查看；
- 批量筛选；
- 批量审阅；
- 外部资料导入；
- 数据导出；
- 必要的人工交换流程。

知识真值仍应落回正式结构化数据。

---

## 4.5 Release：只读发布快照

正式网站不直接读取正在编辑的 `knowledge/`。

正确流程是：

```text
knowledge
   ↓
Validator
   ↓
Gate
   ↓
Candidate Release
   ↓
网站 manifest / search-index / law-index / shards
   ↓
静态网站
```

Release 必须可确定、可追溯，并继续保留 `releaseHash`。

候选 Release 不等于生产 Release。

# 五、核心数据模型

## 5.1 Hazard：隐患实体

负责保存：

- 标题；
- 专业描述；
- 整改措施；
- 分类；
- 适用条件；
- 场所；
- 关键词；
- 别名；
- 生命周期。

隐患本身不直接复制法规全文。

它通过 link 与 clause 建立关系。

---

## 5.2 Law：法规 / 标准身份

Law 只回答：

> “这是哪一部法规 / 哪一个标准？”

主要保存：

- 正式名称；
- 文件类型；
- 发布机关；
- jurisdiction；
- 别名；
- identity key。

同一法规身份不因为修订而重复建立多个 Law。

---

## 5.3 LawVersion：具体版本

LawVersion 回答：

> “现在引用的是这部法规 / 标准的哪个版本？”

必须保存：

- lawId；
- 版本标识；
- 正式名称；
- 标准号 / 文号（适用时）；
- 实施日期；
- 终止日期（适用时）；
- active / upcoming / repealed / unknown 等效力状态；
- 官方来源。

旧版本不能被新版本直接覆盖。

---

## 5.4 Clause：具体条款

Clause 必须属于明确的 LawVersion。

核心字段：

- clause ID；
- lawVersionId；
- articlePath / 标准条号；
- quote 原文；
- sourceUrl。

`quote` 必须保存核验后的法规 / 标准原文，不在原文字段里混入 AI 解释。

---

## 5.5 Link：隐患与条款的适用关系

Link 是 Safety Basis 最重要的语义实体之一。

它回答：

> “这条已经核验正确的法规条款，为什么能够用于这个具体隐患？”

基本角色：

- `direct`：直接、明确的定性或整改依据；
- `supporting`：补充依据；
- `fallback`：确实缺少更直接专项条款时的上位法 / 通用义务兜底。

Link 必须保存 applicability，并经过独立适用性审阅。

条款文字正确，不代表它自动适用于某条隐患。

---

## 5.6 Succession：法规和标准替代关系

用于表达：

- replaces；
- partially_replaces；
- amends；
- supersedes；
- related。

法规 / 标准更新时，优先更新版本和替代关系，再逐条审查受影响 link。

不得只把旧标准号替换成新标准号，然后沿用旧条文和旧适用结论。

---

# 六、法规和标准的核验原则

每一个准备作为正式依据的对象，都要分层判断。

## 6.1 身份核验

确认：

- 正式名称；
- 标准号 / 文号；
- 发布机关；
- 文件类型；
- jurisdiction。

---

## 6.2 版本和时效核验

确认：

- 发布 / 修订版本；
- 实施日期；
- 是否现行有效；
- 是否 upcoming；
- 是否已废止；
- 是否有新版本；
- 是否存在替代、部分替代或修改关系。

历史报告中的引用不能因为“以前用过”就自动视为当前有效。

较新的报告可以优先作为线索，但仍需核对当前版本和时效。

---

## 6.3 条款原文核验

确认：

- 条款属于正确版本；
- 条款号 / 标准条号正确；
- locator 明确；
- quote 与证据原文一致；
- 数字、单位、否定词、例外条件和限定条件没有被改写。

找不到可靠原文时保持 pending，不编造。

---

## 6.4 适用性核验

建立 Hazard → Clause 关系时，至少判断：

- 监管对象是否一致；
- 设备 / 设施是否一致；
- 行业是否适用；
- 场所是否适用；
- 工况和前置条件是否满足；
- 地域是否适用；
- 条款义务是否真正对应现场缺陷；
- 是否存在更直接、更专门的条款。

禁止仅凭关键词相似、同一法规、同一设备名称或同一行业直接判定 verified。

---

# 七、依据选择原则

Safety Basis 不机械按法律位阶从高到低堆砌依据。

应综合考虑：

- 直接适用程度；
- 专业技术针对性；
- 法律 / 标准效力；
- 地域适用性；
- 当前版本有效性。

处理逻辑：

### 有直接专项依据

优先使用直接规定该设备、设施、行为、工艺、场所或技术参数的法规 / 标准条款。

### 同时存在有价值的上位法

可以保留为 supporting basis，用于补充法定义务或责任背景。

### 存在江苏 / 南京地方要求

如果对当前场景实际适用，可以同时保留地方依据。

### 找不到直接技术依据

才使用合适的上位法或通用义务作为 fallback，并明确说明为什么属于兜底。

一个隐患可以有多个依据，但不允许为了显得“依据很多”而堆砌无实际支撑关系的法规。

---

# 八、证据体系

V4 将“条款是否可靠”与“有没有完整全文归档”分开处理。

## Tier A：authoritative-public

官方公开证据，例如：

- 政府官网；
- 立法机关；
- 国家法律法规数据库；
- 国家标准公开系统；
- 法规 / 标准发布机关；
- 官方 PDF。

Tier A 可以直接用于法规身份、版本和条款核验。

---

## Tier B：authoritative-private

用户合法持有的：

- 购买版标准；
- 内部授权原件；
- 私有 PDF；
- 其他可信原始文件。

可以支撑核验，但公开 Git / Release 只保存必要引用、locator 和不泄露原件的引用信息。

---

## Tier C：secondary

包括：

- 第三方转载；
- 搜索摘要；
- 博客；
- 论坛；
- AI 生成内容；
- 其他辅助资料。

Tier C 适合发现线索和交叉核对，但不能单独支撑关键 law / lawVersion / clause 的 verified。

---

# 九、完整全文的定位

Safety Basis 不是“必须先把所有中国 EHS 法规标准全文收齐，才能使用”的系统。

如果已经能够可靠确认：

- 法规 / 标准身份；
- 正确版本；
- 当前效力；
- 具体条款定位；
- 具体条款原文；
- 对当前隐患的适用性；

那么该具体条款可以进入知识库并作为依据。

**完整全文不是每一条隐患发布的统一前置条件。**

全文库的长期价值主要是：

- 搜索；
- 查找潜在条款；
- 交叉核验；
- 私有证据留存；
- 法规更新分析。

# 十、Review 与内容绑定

V4 的正式 review 必须对应当前实体内容。

使用实体级：

`reviewedContentHash`

解决：

> “实体已经改了，但旧 review 还被继续当成有效结论”的问题。

原则：

- 只绑定被审阅实体本身的 canonical 内容；
- 不恢复 V3 那种对整张依赖图计算通用 dependencyHash 的方式；
- Link 的 applicability review 可以显式绑定当前 hazard 和 clause 的 context hash，因为它本身就是二者之间的语义判断。

这样既能防止陈旧 review，又避免小修改导致全库大面积机械失效。

---

# 十一、Validator 与 Gate

Validator 和 Gate 必须分工明确。

## Validator

负责判断数据结构是否健康，例如：

- JSON / schema；
- Stable ID；
- 唯一性；
- 外键；
- review hash；
- 重复实体；
- lifecycle；
- 图完整性；
- 私有字段泄漏；
- 数据结构错误。

## Gate

负责判断内容是否允许进入正式 Release，例如：

- law identity 是否 verified；
- lawVersion 是否有效；
- clause text / locator 是否 verified；
- link applicability 是否 verified；
- hazard 是否有至少一个 qualifying link；
- upcoming / repealed / unknown 是否被错误用于当前依据；
- 是否泄露私有资料。

Hazard 要进入当前正式 Release，至少需要一个完整通过链式 Gate 的 `direct` 或 `fallback` link。

`supporting` 不能单独支撑一个 Hazard 发布。

一个附加 link 仍为 pending，不应在已有可靠 direct/fallback 的情况下机械拖死整个 hazard；未通过的 link 本身不进入 Release，并进入报告或待核验队列。

---

# 十二、隐私与版权边界

公开 Release 必须采用字段 allowlist。

不得公开：

- 企业客户名称等不应公开的项目来源；
- 个人信息；
- 私有 Google Drive 文件 ID / 路径；
- 本地绝对路径；
- API key / token；
- 私有报告正文；
- 付费标准整份正文；
- 受版权或许可限制的附件原件；
- 内部 raw payload / legacy payload；
- 仅用于私有证据追踪的引用信息。

可以在许可允许范围内公开法规 / 标准名称、编号、条款号、必要原文和来源说明。

# 十三、日常知识生产流程

## 13.1 用户提供一条新隐患

流程：

```text
识别现场问题
  ↓
搜索已有 hazard
  ↓
能复用则复用；否则建立 candidate hazard
  ↓
搜索已有 direct / supporting / fallback basis
  ↓
需要时联网核验当前法规 / 标准
  ↓
建立或更新 law / lawVersion / clause
  ↓
逐条判断 applicability
  ↓
建立 link
  ↓
生成 / 更新 review
  ↓
Validator + Gate
  ↓
候选 Release
```

---

## 13.2 用户提供检查表 / 评价报告

报告本身不是直接批量入库的“真值”。

应：

1. 提取可复用隐患；
2. 提取法规 / 标准引用；
3. 提取整改措施和适用场景；
4. 与已有知识查重；
5. 历史引用重新核对版本和时效；
6. 正确内容复用；
7. 新内容进入 candidate / pending；
8. 完成核验后再转 verified。

最新报告可以作为高优先级线索，但不能免除时效核验。

---

## 13.3 出现新法规 / 新标准

流程：

```text
确认法规 / 标准身份
  ↓
建立新 lawVersion
  ↓
确认 effectiveDate / validityStatus
  ↓
建立 succession
  ↓
识别旧版本受影响 clause / link
  ↓
逐条检查是否需要新 clause
  ↓
逐条重新判断 applicability
  ↓
更新当前依据
```

禁止把新版本标准号直接批量替换到旧条款上。

---

# 十四、批量任务质量原则

Safety Basis 可以批量迁移、批量扫描、批量生成候选，但 **不能批量制造“已经人工语义核验过”的假象**。

长期原则：

- 批量任务优先生成 candidate；
- verified 必须有真实核验依据；
- link applicability 尤其需要逐条判断；
- 一个 evidence 不能机械证明一批语义不同的 link；
- r8 历史批量错误关联不得恢复；
- 不确定内容保持 pending；
- 宁可少发布，也不要让错误法规依据进入现场使用场景。

---

# 十五、V3 → V4 建设路线

当前 V4 改造总体沿以下主线完成。

## Phase 1：冻结 V3 基线

确认最新 SQLite、全文库、Release、源码和关键统计，建立不可混淆的迁移基线。

## Phase 2：V4 Chat-first 架构

明确 GitHub、Google Drive、SQLite、Excel、Release 和网站之间的职责。

## Phase 3：V4 Gate 设计

把内容正确性硬门禁与技术审计 Warning 分开。

## Phase 4：V3 → V4 数据映射

明确所有核心实体和审阅 / 证据如何迁移，并保留 Stable ID。

## Phase 5：只读迁移原型

从冻结 V3 中生成 V4 candidate，不反写 V3。

## Phase 6：迁移现有有效知识

优先迁移已经可靠核验的：

- law；
- current lawVersion；
- clause；
- hazard；
- link；
- evidence；
- succession。

pending、失效、效力不明和 r8 错误数据不得为了数量强行升级。

## Phase 7：法规与标准核验框架

建立长期可持续的核验队列和优先级体系。

重点优先：

- 当前网站正在使用的依据；
- 高使用频率法规；
- 高风险设备 / 作业标准；
- 影响大量隐患的共享条款；
- 江苏 / 南京常用法规；
- 用户实际工作中高频隐患；
- pending hazard 缺失的专项依据；
- 存在新旧版本替代风险的法规 / 标准。

## Phase 8：历史报告引用复核

按价值和使用频率复核，不要求无差别重做所有历史报告。

## Phase 9：V4 Validator

实现结构和一致性校验。

## Phase 10：V4 Gate

实现法规身份、版本效力、条款、适用性和隐私等发布门禁。

## Phase 11：V4 网站构建

优先兼容现有前端，通过 adapter 生成现有网站所需 manifest / index / shards；先替换知识生产架构，不急于重写 UI。

## Phase 12：V4 候选 Release

生成独立候选发布包和可读 Gate 报告。

## Phase 13：V3 / V4 对比验收

比较：

- Stable ID；
- 隐患数量和内容；
- 法规身份和版本；
- 条款原文；
- link 关系；
- 搜索；
- 页面；
- 私有信息；
- Release inclusion。

发现差异时判断是 V4 回归还是 V4 正确修复了 V3 历史问题。

## Phase 14：真实差异修复

只修真实问题，不为了和旧数据数字完全一致而复制旧错误。

## Phase 15：持续法规核验与扩库

核心 V4 稳定后，持续补充法规、标准、条款和隐患依据。

这个阶段是长期维护能力，不以“把所有法规全文全部收齐”作为完成标准。

## Phase 16：最终验收

完成数据、门禁、法规、构建、搜索、页面、发布包和隐私验收。

## Phase 17：生产切换

生产网站切换属于独立决策。

在用户明确批准生产切换前，V4 应保持候选状态，不直接替换 `main` 或生产 selection。

# 十六、项目完成后的长期运行方式

V4 正式稳定后，Safety Basis 不再是一次性项目，而是持续生长的知识库。

未来维护应形成几个长期循环：

### 隐患循环

```text
新隐患 → 查重 → 补专业描述 → 核验依据 → 入库 → 发布
```

### 法规更新循环

```text
新法规 / 新标准 → 版本核验 → succession → 影响分析 → 更新 link → 发布
```

### 待核验清理循环

```text
pending → 按价值排序 → 找证据 → 核版本 → 核条款 → 核 applicability → verified / rejected
```

### 网站发布循环

```text
knowledge → validate → gate → release → site build → QA → production selection
```

# 十七、项目文档层级与新窗口续接

为了让任何新的 Chat / AI 在没有旧聊天上下文时也能继续工作，项目状态不依赖模型记忆。

文档职责固定如下：

## `docs/PROJECT_PLAYBOOK.md`

本文件。

负责：

- 项目最终目标；
- 整体框架；
- 长期原则；
- 建设路线；
- “我们到底要干什么”。

属于长期稳定说明书。

## `docs/ARCHITECTURE_V4_CHAT_FIRST.md`

负责 V4 具体技术架构和数据模型。

## `docs/GATE_V4.md`

负责发布门禁、review、evidence、hash、link applicability 和隐私规则。

## `docs/MIGRATION_V3_TO_V4.md`

负责 V3 → V4 的字段和状态迁移细节。

## `docs/CHAT_HANDOFF.md`

负责实时施工状态。

必须记录：

- 当前 Phase；
- 当前分支 / HEAD；
- 最近完成事项；
- 修改文件；
- 校验结果；
- 当前关键统计；
- 未完成事项；
- 风险和阻塞；
- 下一步第一动作。

因此，新窗口续接时，应先：

```text
PROJECT_PLAYBOOK.md
        ↓
CHAT_HANDOFF.md
        ↓
核对当前 GitHub HEAD 和实际文件
        ↓
按需读取 ARCHITECTURE / GATE / MIGRATION
        ↓
继续当前下一项工作
```

如果 `CHAT_HANDOFF.md` 与 GitHub 实际落盘成果不一致，以更晚的真实 commit / 文件为准，并修正 handoff。

# 十八、最终验收目标

Safety Basis V4 达到可验收状态时，应满足：

- V4 知识维护不再强依赖本地 Code Agent；
- Chat 可以直接读取和修改结构化知识；
- Stable ID 和历史知识关系保留；
- 现行法规 / 标准版本能够明确区分；
- 条款原文有可靠证据；
- 隐患—条款适用性经过独立判断；
- pending 不会混进正式依据；
- 找不到整本标准全文时，可靠局部条款仍可使用；
- 直接依据、supporting 和 fallback 能够区分；
- 江苏 / 南京地方依据能够正确建模；
- 历史报告不会自动污染当前版本；
- 私有资料不会泄露到公开 Release；
- Validator / Gate 能阻止真正错误内容；
- 不重要的历史技术元数据问题不会无意义拖死正确内容；
- V4 可以生成确定性候选 Release；
- 网站搜索、筛选、详情和法规关系正常；
- V3 / V4 差异经过解释和验收；
- 生产切换前能够清楚知道网站最终发布的具体 Release。

# 十九、最终原则

Safety Basis 的优先级始终是：

> **正确性 > 可追溯性 > 实用性 > 可维护性 > 数量。**

系统可以复杂，但复杂度应留在后台。

用户最终使用时应该足够简单：

> **把隐患发过来，就能得到专业描述、最合适的现行依据、原文、整改措施和适用说明。**

所有架构、数据库、Review、Evidence、Gate、Release 和网站建设，最终都服务于这个目标。
