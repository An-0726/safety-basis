# 数据模型 V2

## 设计目标

数据模型要同时满足：

1. **隐患速查**：现场问题能够搜索到专业描述、法规原文和整改措施。
2. **法规复用**：同一法规条款只保存一次，可被多条隐患引用。
3. **法规反查**：从一部法规或一个条款可以找到所有关联隐患。
4. **持续更新**：法规修订、废止、替代时可追踪状态，不需要在几千条隐患中重复修改原文。
5. **大规模运行**：维护源完整规范化，运行层再生成轻量索引与分片，避免一次加载所有正文。

## 1. `hazards.json`

核心字段：

| 字段 | 含义 |
| --- | --- |
| `id` | 稳定唯一 ID，发布后原则上不复用 |
| `title` | 隐患名称 |
| `aliases` | 常见别称 / 搜索同义词 |
| `places` | 适用场所标签 |
| `category` | 专业主题 |
| `keywords` | 检索关键词 |
| `description` | 隐患专业描述 |
| `measures` | 整改措施 |
| `note` | 适用条件、判定边界、兜底说明 |
| `mode` | `直接适用` / `条件适用` / `上位法兜底` |
| `status` | `待核验` / `已核验` / `已失效` |
| `checked` | 最近一次核验日期 |

隐患记录不直接保存法规全文。

## 2. `laws.json`

| 字段 | 含义 |
| --- | --- |
| `id` | 法规 / 标准唯一 ID |
| `name` | 现行正式名称 |
| `aliases` | 旧称、简称、标准号常见写法 |
| `level` | 法律、行政法规、部门规章、强制性国家标准等 |
| `scope` | 全国、江苏／南京、南京等 |
| `status` | `现行有效` / `即将生效` / `已废止` / `待核验` |
| `checked` | 最近一次效力核验日期 |
| `sourceUrl` | 可追溯来源 |
| `effectiveDate` | 实施日期（有可靠数据时填写） |
| `replaces` / `replacedBy` | 标准或法规替代链 |

## 3. `clauses.json`

只收录数据库实际引用的条款，不要求把整部法规全文复制进仓库。

| 字段 | 含义 |
| --- | --- |
| `id` | 条款唯一 ID |
| `lawId` | 所属法规 |
| `article` | 条、款、项 / 标准条款号 |
| `quote` | 经核验的原文 |
| `status` | 条款核验状态 |
| `checked` | 条款原文核验日期 |
| `sourceUrl` | 条款有独立来源时填写；否则继承法规来源 |

## 4. `links.json`

这是隐患和法规条款之间的多对多关系表。

| 字段 | 含义 |
| --- | --- |
| `hazardId` | 隐患 ID |
| `clauseId` | 法规条款 ID |
| `role` | 依据角色，例如“优先直接标准”“地方直接依据”“上位法兜底” |
| `priority` | 同一隐患详情页中的显示顺序 |

## 5. 派生运行数据 `data/`

`tools/build-data.mjs` 会生成：

- `manifest.json`：版本、数量、健康状态、分片列表；
- `search-index.json`：隐患轻量搜索索引；
- `law-index.json`：法规搜索和反查索引；
- `taxonomy.json`：主题、场所、法规层级等筛选项；
- `hazards/*.json`：隐患详情分片；
- `clauses/*.json`：条款正文分片。

运行层可以随数据量增加调整分片，不改变维护源模型。

## 6. 关于报告来源

完整报告、现场照片、企业内部资料不进入公开仓库。后续如需保存来源追溯信息，应只保存公开安全的来源标识，或者在私有 Drive 台账中维护“来源文件 ↔ 数据库 ID”的映射。
