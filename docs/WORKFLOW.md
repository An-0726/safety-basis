# 报告 / 检查表持续入库工作流

目标不是“把整份报告上传网站”，而是把报告中的可复用安全知识持续沉淀到数据库，同时避免重复、过期依据和私有资料泄露。

## 一、资料进入私有资料源

新报告、检查表、整改通知、法规台账等首先保留在 Google Drive 等私有位置。公开 GitHub 仓库不直接存放企业完整报告或现场照片。

## 二、抽取候选知识

从新资料中提取：

- 现场隐患 / 检查项目；
- 法规、标准名称与条款号；
- 可用法规原文；
- 整改措施；
- 适用行业、场所、设备和条件；
- 可能已废止或被替代的旧依据。

候选内容只是原始语料，不能直接视为已核验数据库记录。

## 三、与现有库比对

对每条候选内容进行：

- 同义隐患合并；
- 一个检查项目包含多个独立义务时拆分；
- 已经是负面隐患描述的内容规范化，不机械反写；
- 无法形成可检查缺陷的状态确认不强行入库；
- 已存在法规、条款优先复用现有 ID；
- 同一条款只建立新的关联，不重复保存法规全文。

## 四、法规核验

优先级：

1. 现行强制性标准 / 直接专门条款；
2. 法律、行政法规、规章；
3. 江苏 / 南京地方规定；
4. 确无直接条款时才使用明确标注的上位法兜底。

核验内容包括名称、版本、条款号、原文、来源、适用范围、效力状态和替代关系。拿不准的记录为“待核验”。

## 五、更新维护源

按需要修改 `content/hazards.json`、`laws.json`、`clauses.json`、`links.json`。

每次数据批次完成后更新 `content/settings.json` 中的 `dataVersion` 和 `generatedAt`。

## 六、构建与校验

```bash
node tools/build-data.mjs
```

构建脚本会检查：

- ID 重复；
- 空字段和非法状态；
- 隐患 / 条款 / 法规断链；
- 已核验条款缺失原文或来源；
- 非法 URL；
- 分片与搜索索引生成。

## 七、提交和发布

提交维护源与生成后的 `data/`。GitHub Actions 会重新构建并检查派生数据是否同步。GitHub Pages 继续从仓库静态发布，不需要额外服务器。

## 八、后续法规更新

法规修订时：

1. 更新 `laws.json` 的效力状态和替代链；
2. 新建 / 更新相关 `clauses.json`；
3. 查找受影响的 `links.json`；
4. 必要时更新隐患描述、整改措施、适用说明；
5. 提升 `dataVersion`，重新构建并提交。

这样可以避免在几千条隐患记录中反复复制和替换相同法规全文。
