# 报告 / 检查表持续入库工作流

目标不是“把整份报告上传网站”，而是把报告中的可复用安全知识持续沉淀到数据库，同时避免重复、过期依据和私有资料泄露。

当前入口见 [入库与合并](ADMISSION.md)、[Excel 编辑](EXCEL_EXCHANGE.md)、[法规目录及身份合并](CATALOG.md)、[核验与发布](VERIFICATION_PUBLISH.md)、[全文库](FULLTEXT_LIBRARY.md)。工具链已完成真实多文件演练，尚未切换生产；具体核验完成范围见 [交付报告](DELIVERY_20260909.md)。

## 一、资料进入私有资料源

新报告、检查表、整改通知、法规台账等首先保留在私有位置；可导入表格放在 `source/imports/`。程序按文件哈希归档原件，保存来源路径、Sheet、行号及解析配置。私有目录由 Git 忽略，需独立备份。

多布局来源可用注册表入口按 Sheet 和明确表头组合路由，再复用 `intake.py` 保存候选；法规台账进入独立的 `law-registers.sqlite3`，检查/隐患进入 `intake.sqlite3`。未知或同等候选布局会拒绝并留下诊断：

```text
python tools/pipeline/imports.py source/imports --registry source/mappings/registry.json
```

## 二、抽取候选知识

从新资料中提取：

- 现场隐患 / 检查项目；
- 法规、标准名称与条款号；
- 可用法规原文；
- 整改措施；
- 适用行业、场所、设备和条件；
- 可能已废止或被替代的旧依据。

候选内容只是原始语料，不能直接视为已核验数据库记录。

来源查看表前三列为隐患描述、依据法规、法规原文。符合项描述留白，保留依据与原文；从规范要求拆出的通用隐患模板另存，不改变原报告现场结论。报告第五章自动提取尚未集成，应先核对提取质量再导入。

## 三、与现有库比对

对每条候选内容进行：

- 同义隐患合并；
- 一个检查项目包含多个独立义务时拆分；
- 已经是负面隐患描述的内容规范化，不机械反写；
- 无法形成可检查缺陷的状态确认不强行入库；
- 已存在法规、条款优先复用现有 ID；
- 同一条款只建立新的关联，不重复保存法规全文。

## 四、法规核验

优先级：

1. 现行强制性标准 / 直接专门条款；
2. 法律、行政法规、规章；
3. 江苏 / 南京地方规定；
4. 确无直接条款时才使用明确标注的上位法兜底。

核验内容包括名称、版本、条款号、原文、来源、适用范围、效力状态和替代关系。拿不准的记录为“待核验”。

## 五、更新母库

通过 `admission.py plan/propose/apply` 审阅候选入库或复用；检查项目必须拆分或暂缓。已有母库记录通过 Excel 导出、修改提案、单事务提交。隐患合并保留旧身份和来源，目标退回待核验。

官方证据通过 `review.py evidence` 登记，实际核验决定通过 `plan/propose/apply` 提交。状态、内容版本和证据必须一致；不直接维护 `content/*.json` 或 `data/*.json`。

## 六、构建与校验

```text
python tools/pipeline/manage.py site --as-of YYYY-MM-DD --output source/releases/NEW_RELEASE
python tools/pipeline/manage.py verify-site --output source/releases/NEW_RELEASE
```

构建脚本会检查：

- ID 重复；
- 空字段和非法状态；
- 隐患 / 条款 / 法规断链；
- 各层当前内容、依赖版本与最新核验是否一致；
- 法规有效期间、复核日期、官方证据 URL 和原件 SHA；
- 待核验关联、条款冲突及公开字段白名单；
- 分片与搜索索引生成。

## 七、提交和发布

生成隔离包及独立私有增减/阻断报告，公开快照可提交供 CI 重建。更新 `source/releases/site-selection.json` 后，分支 CI 只构建托管 artifact；当前生产仍保留遗留基线，正式发布仅在 `main` 手动触发。生产切换前需审阅完整增减报告。统一命令 `python tools/pipeline/manage.py site --as-of YYYY-MM-DD --output NEW_DIR` 同时生成网站资源、JSON、索引、全文和发布清单。

## 八、后续法规更新

法规修订时：

1. 通过母库编辑提案更新法规版本的效力状态；
2. 重新构建隔离包，门禁按共享法规依赖列出受影响隐患；
3. 新版法规和条款使用新身份/版本提案，不覆盖旧原文（创建接口待补齐）；
4. 核对新条款及关联适用性，必要时更新隐患描述、整改措施、适用说明；
5. 重新核验、构建并审阅发布差异，部署完成后静态网站才会反映更新。

这样可以避免在几千条隐患记录中反复复制和替换相同法规全文。
