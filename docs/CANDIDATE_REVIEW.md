# 待审核候选处理规则

本文件是当前唯一的候选处理规则。历史批次数字和旧处理记录不在主分支保留，需追溯时查看 Git 历史。

## 1. 候选的含义

`lifecycle=proposed` 表示记录已经进入结构化知识源，但法规版本、具体条款、原文证据、适用性或去重结论尚未全部满足正式门禁。

候选不是正式法律依据，也不是法规效力状态。候选不得因为“已经有名称/条款要点/搜索摘要”就转为正式。

常见 `proposalStatus`：

- `workbook_revised_pending_clause_rebind`：字段已修订，待重新绑定精确条款和证据；
- `basis_catalog_only`：只有法规题录或官方入口，没有可核验具体条款；
- `basis_name_unresolved`：法规身份、编号或版次尚未确认；
- `same_title_review`：与已有隐患同名或高度相似，必须先判断合并还是保留。

## 2. 当前展示规则

- `knowledge/` 可以保留候选，防止未完成工作丢失；
- 网站“隐患速查”默认只显示 `已核验` 记录；
- 候选只有在明确选择候选状态时才显示，不能与正式依据混在默认结果中；
- 重复/合并记录不得重复发布为另一条当前隐患。

## 3. 转正固定流程

1. 确认隐患对象、场景和专业描述，先做重复/合并判断；
2. 确认法规或标准的唯一身份、编号和适用版本；
3. 核对发布日期、实施日期、废止/替代关系；
4. 从官方原文或合法保存的原始 PDF 中定位具体条、款、项/标准条号；
5. 建立或复用 `knowledge/clauses/` 条款，保存逐字原文和来源；
6. 建立证据、条款审核、隐患审核和直接关联审核；
7. 只有完整 Gate 通过后，才把候选转为 `active`；
8. 重新构建、校验并更新 README 当前基线。

## 4. 禁止事项

- 不把 AI 摘要、搜索摘要、Excel“依据条款要点”当成法规原文；
- 不仅凭文件名或标准名称判断现行性；
- 不把尚未实施的新版本自动当作当前现行版本；
- 不因标题相似直接删除，必须比较对象、场景、整改措施和依据；
- 不为了前台整洁重编号已有稳定 ID；
- 不把候选数量报成正式已核验数量。

## 5. 当前数据口径

2026-09-14 基线中，`knowledge/` 有 517 个 `proposed` 实体；新版 1929 条目标集在重复抑制后有 512 条当前候选。两者不是同一个统计口径。以后以 `README.md`、`docs/HANDOFF.md` 和实时 Gate 输出为准，不再维护按日期命名的候选手册。
