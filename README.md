面向工贸企业安全检查与评价报告的法规、标准、条款和隐患关联库。国家层面为主，江苏、南京地方依据为补充。

在线站点：<https://an-0726.github.io/safety-basis/>

## 二、哪些目录可以改，哪些不能直接改

### 日常允许人工维护

- `knowledge/`：核验后的法规身份、版本、条款、隐患和关联。
- `source/publication/`：公开目录、官方入口、版权允许公开的全文。
- `web/`：网站前端。
- `tools/`：构建、核验、迁移与维护工具。
- `docs/`：当前规则、交接说明和阶段记录。

### 不得作为人工数据源直接修改

- `source/releases/current/`：**构建产物**。修改正式数据后应重新构建，不能在这里手工修数据。
- `dist/local/`：**本地生成物**。可删除重建，不是母库。
- OCR 文本、HTML 阅读页、搜索索引：均为检索/展示派生物，不得反向冒充法规原文。

### 不得上传 GitHub

- `source/library/` 内的私有 PDF、SQLite、OCR、内部归档。
- 企业报告、照片、未脱敏附件、内部台账。
- 未取得公开分发权限的标准全文。

## 三、法规、版本和来源的统一规则

法规库必须区分三个概念：

1. **法规身份**：例如“危险化学品安全管理条例”。同一法规只建立一个身份。
2. **法规版本**：例如某次修订版、新旧 GB/GB/T 版本。真实不同版本分别保存，不因名称相同而删除。
3. **来源记录**：国务院网站、国家法律法规数据库、标准平台、PDF 原件等。多个来源可以指向同一个法规版本，**不能因为来源不同就在前台生成两部法规**。

稳定的内部 ID（如 `LF_*`、`LV_*`、`C_*`、`H_*`）用于关系绑定和历史追踪，原则上**不因前台显示不好看而重编号**。前台应显示规范名称、文号/标准号、版本和效力状态；技术 ID 仅供后台排查。

法规去重不得只按标题删除。至少要判断：

- 同一法规、同一版本、不同来源 → 合并为一个版本，保留多个来源；
- 同一法规、不同版本 → 均保留，建立替代/生效关系；
- 新版已发布但尚未实施 → 标记 `upcoming`，不得冒充现行依据；
- 目录元数据与已核验正式版本重复 → 目录映射到正式版本；
- 完全重复导入 → 合并记录但保留旧 ID 的追溯关系。

## 四、正式法规引用的硬门禁

正式隐患依据不能使用 AI 摘要、搜索摘要或“条款要点”冒充法条。进入正式发布层的法规依据至少应满足：

1. 法规/标准身份明确；
2. 版本明确；
3. 效力/实施状态明确；
4. 能定位到具体条、款、项或标准条号；
5. 有对应原文；
6. 有官方来源 URL 或可追溯证据快照；
7. 条款号与原文核对一致；
8. 条款适用于对应隐患和适用场景；
9. 审核记录仍绑定当前内容；
10. AI 只能辅助发现线索，不能替代法规原文证据。

不满足上述条件的记录应保留为候选/待核验，不得作为正式法律依据输出。

## 五、候选与公开发布

当前知识源中允许存在 `proposed` / 待审核候选，用于保存尚未完成条款、证据或适用性回绑的工作成果。

**候选不是法规效力状态。** 它表示该隐患/关联尚未满足正式发布门禁。

后续维护目标：公共正式站与内部审核工作台职责分离。公共正式页面优先展示已核验依据；候选数据保留在知识源中供审核，不得因整理界面而删除。

## 七、仓库整洁规则

### 当前主线文档

- `README.md`：项目入口、当前架构、当前基线和维护约束。
- `docs/ARCHITECTURE.md`：技术架构。
- `docs/MAINTENANCE.md`：日常维护步骤。
- `docs/LEGAL_STATUS_POLICY.md`：法规效力与版本规则。
- `docs/HANDOFF.md`：给下一位维护者的当前交接摘要。

### 日期命名文档

类似 `*_20260913.md`、`*_20260914.md` 的文件只用于保存某次整改、核验或阶段交付记录，**不得被当作当前架构说明**。若后续同类阶段记录继续增加，应统一移入 `docs/history/` 或依赖 Git 历史保存，避免根 `docs/` 长期堆积多个“最终版”。

### 旧版本处理原则

- 不在当前主线保留多个 `v1/v2/v3/final/final2/latest` 目录或重复发布包。
- 能由 Git 历史恢复的旧生成物，不再长期保留在当前树中。
- 私有全文历史备份保留在仓库外，例如：`D:\ESH\ESH_Codex\archive\...`。
- 删除或迁移旧资料前，必须先确认没有被当前构建、测试、ID 映射或本地 agent 引用。

## 八、变更记录要求（必须执行）

**以后任何会影响接手理解或正式结果的变更，都必须同步更新本 README。** 至少包括：

- 仓库目录或主线架构变化；
- 法规身份/版本归并规则变化；
- 发布器、公开范围或候选策略变化；
- 大批量法规/隐患回灌；
- 当前基线数量发生实质变化；
- 本地私有法规库位置或构建方式变化；
- 删除、迁移历史目录或停用旧工具。

每次提交说明要回答四个问题：**改了什么、为什么改、影响哪些数据、是否需要重建/重新审核。**

小型前端样式、拼写修复等不改变数据含义的修改可以只写 Git commit；涉及架构、数据口径和发布边界的修改必须同时更新 README。

## 九、验证与构建

```text
py -3 tools/v4/validate_all.py
py -3 tools/v4/strict_release_audit.py
py -3 tools/v4/build_unified_release.py --out source/releases/current
py -3 tools/v4/verify_unified_bundle.py --bundle source/releases/current
py -3 -m unittest discover -s tools/pipeline/tests -v
node --test tests/*.test.mjs
```

如果法规目录、隐患关系或私有全文库发生更新并通过验证，本地最终版重新生成：

```text
py -3 tools/build_local_release.py
```

CI只验证并发布 `source/releases/site-selection.json` 指向的包。任何法规效力、条款内容或隐患适用关系变更，都必须经过证据核验，不能仅凭文件名、网页可访问性或模型判断直接生效。
